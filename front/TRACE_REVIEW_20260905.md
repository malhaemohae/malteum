기획 §11.4는 저장된 타임스탬프대로 TRACE를 재생하도록 정한다. 따라서 시간 간격을 보존하는 것 자체와, 사용자가 빈 화면을 보며 기다려야 하는 UX 결함을 구분한다. 최초 발화 건너뛰기/재생 시간 기준 변경은 기록 시간을 변조하지 않는 방식으로 명시적으로 설계해야 한다.

## 프론트에서 확인한 문제

1. `components/application.tsx:27`의 시계는 마이크가 켜진 때만 흐른다. TRACE는 발화 수신 때만 `lib/workspace-model.ts:45`에서 시간이 바뀌어, 초기 무발화 구간에 00:00으로 정지해 보인다. 재생 중·다음 이벤트 대기·완료 구분이 없다.
2. `components/operations.tsx:48`의 TRACE 버튼은 실행 중 여부만 확인한다. 기존 TRACE 이력이나 발화가 없는 세션에도 활성화되고, `components/application.tsx:127`은 그 세션 ID를 새 `source_session_id`로 넘긴다.
3. `ended`가 오면 일반 상담과 동일하게 새 TRACE 세션의 리포트로 이동한다. 원본 리포트 열기와 재생 완료 후 결과 유지 정책도 구분해야 한다. 이번 원본은 모든 요약 수치가 0이어서 리포트 수치 불일치까지 입증한 것은 아니다.

## 백엔드/저장 계층에서 확인한 문제

- 원본 발화 없는 TRACE도 생성되고 `ready`가 온다. 빈 재생 대상이라는 오류나 완료 신호는 오지 않는다.
- 원본 이벤트를 모두 보낸 뒤 자동 완료 신호가 오지 않는 것을 재현했다.
- PostgreSQL을 읽기 전용 SELECT로 확인했을 때 기존7개 TRACE와 새 진단2개의 `sessions.source_session_id`가 모두 NULL이었다. 진단기는 생성 POST에 실제 원본 ID를 명시했다. TRACE 자체에 원본 발화가 복제되지 않는 것은 정상일 수 있지만, 재시작/재조회에서 원본 연결을 복원할 수 있는 영구 참조가 필요하다. 서버 재시작 후 재생은 이번에는 실행하지 않았다.
- 내부 Python 구현은 변경하거나 읽지 않았다. API/WS 계약, 실제 요청·응답, SQL 메타데이터로 확인한 결과다.

## 수정 범위 제안 — 미실행

- M1: TRACE 원본 연결 영구 저장/조회, 빈 대상 거부 또는 원본 따라가기, 완료 메시지 전달. 초기 대기 건너뛰기를 도입한다면 원본 시각과 재생 시계를 분리.
- M4: 원본 상담과 TRACE 이력 구분, 재생 가능한지 사전 확인, 대기/재생/완료 상태 표시, 원본 리포트 연결. 프론트가 자체 판정을 만들거나 원본 이벤트를 수정하지 않는다.
