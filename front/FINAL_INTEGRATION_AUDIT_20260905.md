## 8. 최종 완료에 필요한 순서

1. 프론트에서 쉬운 말 요청→대기→결과 표시를 바로잡고, 보고서·인쇄물의 내부 필드 노출을 제거한다.

6. 로컬 검수가 통과한 커밋을 확정한 후 배포 환경의 버전·API·WS·음원·근거 원문을 별도 확인한다.

### 재현과 원인

- 새 DB 세션 생성 및 모든 실제 WS 연결을 차단한 브라우저에서, 커밋된 `ready`·숫자 경보 fixture를 그대로 사용했다. 카탈로그 GET은 실제 서버를 조회했다.
- 필요 서류를 두 번 누르면 동일한 요청이 두 번 전송됐다. 기준 확인도 요청 payload가 확인됐다.
- 응답을 의도적으로 보류했을 때 두 버튼은 계속 활성화되고, 안내에는 **“녹음 시작 버튼을 눌러 상담을 시작하세요.”**가 남았다. 사용자가 요청의 접수·대기·실패를 구분할 수 없다. 이 검사는 서버 무응답/지연 상황의 프론트 동작을 재현한 것이며, 실제 서버가 이번에 응답을 누락했다는 의미가 아니다.
- 기존 숫자 경보가 있는 상태에서는 버튼을 눌러도 해당 경보가 계속 보였다. 코드상 documents/briefing 응답도 공통 개입 큐의 우선순위 6으로 들어가므로 위험·금지·숫자·재진술·답변·미고지 안내보다 뒤에 놓인다. 도착한 응답이 긴급 경보를 덮어쓰지 않는 것은 맞지만, 사용자가 직접 요청한 서류/기준을 확인할 별도 수단이 없다.
- 실제 DB의 기존 세션 `01M1QYFCS6MHQA8GJSXSA3PJVS`에서 documents 이벤트 `01M1QYM5Y4PW1T5Z07AGJ48X00`, briefing 이벤트 `01M1QYMHH80TW8HPBMNNJ0DCY7`를 조회했다. 백엔드 기능 자체가 비어 있다는 주장은 맞지 않는다. 새로운 요청을 실제 서버에서 생성한 검사는 아니다.

### 기획에 맞는 정리 방향 — 아직 미구현

- **녹음**은 주 조작 버튼으로 유지한다.
- **필수 안내**는 기존 체크리스트 탭을 사용하고 큰 중복 바로가기 카드가 필요한지 재검토한다.
- **필요 서류**는 기획 §7.1 ④의 “팩 데이터, 정적 표시”대로 즉시 보여주는 참조 목록이 맞다. 실시간 판단 큐나 녹음에 의존할 이유가 없다. 대출 팩처럼 데이터가 없으면 명확한 빈 상태를 표시한다. 서류 접수·서명 상태 관리까지 구현된 것처럼 표현하지 않는다(§19 후속 범위).
- **기준 확인**은 실제 기능에 맞게 상담 기준/브리핑 열람으로 명명하고, 현재 선택한 팩·필수 항목을 참조하게 한다. 규정 검증을 새로 수행하는 듯한 이름과 큰 액션 카드는 피한다.
- 화면에는 상담 대화와 현재 개입이 중심으로 남아야 한다. 정적 참조가 경보 큐에 섞여 작동 여부를 알 수 없게 만드는 구조를 해소해야 한다.
