## 1. 제품의 한 문장

말틈은 은행원과 고객의 대화를 듣고 규정 팩의 필수 안내, 금지 표현, 숫자 불일치, 위험 신호를 실시간으로 확인해 주며, 상담이 끝난 뒤 문서 근거가 붙은 리포트를 남기는 상담 지원 도구다.

핵심은 상담원을 대신해 판단하는 것이 아니라, 상담원이 놓치기 쉬운 설명을 한 가지씩 보여 주고 근거를 바로 열어 주는 것이다.

## 2. 무엇을 기준으로 판단했는가

문서마다 역할이 다르므로 다음 우선순위로 대조했다.

| 우선순위 | 기준 | 확인하는 내용 |
| --- | --- | --- |
| 1 | 실행 코드와 계약 스키마 | 실제 화면, API·WebSocket 메시지, 이벤트 필드, 상태 전이 |
| 2 | 현재 fixture·시나리오 | 현재 발행된 팩, 이벤트 수, 기대 결과, 상품명·숫자 |
| 3 | 기획·디자인 문서 | 만들고자 하는 제품 범위, 화면 역할, UX 원칙 |
| 4 | 과거 프론트 문서·로컬 예시 | 이미 구현된 폴백과 이전 시연 문구. 현재 기준과 다르면 차이로 기록 |

기획의 목표와 실제 구현을 같은 사실처럼 쓰지 않았다. 현재 프론트 기준은 백엔드 fixture의 ICBC 원화 정기예금·하나은행 가계 신용대출 팩과 일치한다.

## 4. 최종 사용자 플로우

```text
랜딩에서 서비스 이해·상담 시작
  → 상담 전 브리핑
  → 대시보드 진입
  → 녹음 시작/종료
  → 오디오 전송·전사
  → 판정·진행률·근거 생성
  → 현재 개입 확인·수동 보완·근거 확인
  → 상담 종료
  → 종료 리포트
  → 세션 이력·TRACE 재생
  → 새 상담
```

### 4.1 순서별 행동·트리거·출력·다음 단계

| 순서 | 사용자의 행동 | 시스템 트리거 | 사용자가 보는 정보 | 다음 행동 |
| --- | --- | --- | --- | --- |
| 0. 랜딩 진입 | 페이지를 연다 | `MarketingLanding` 렌더링 | 서비스 한 줄 가치, `상담은 자연스럽게. 근거는 또렷하게.`, 녹음→전사→판정→근거의 개념, 상담 화면 미리보기, CTA | `상담 시작하기` |
| 1. 상담 시작 | 랜딩 CTA를 누른다 | 프론트 로컬 세션 생성 후 `briefing` 화면으로 이동 | 기본 시연 시나리오와 브리핑 확인 안내 | 브리핑 기준 확인 |
| 2. 브리핑 로드 | 브리핑을 읽는다 | `GET /api/packs/{pack_version}/briefing?customer_type=...`; 실패·불일치 시 프론트 기준으로 폴백 | 시연 시나리오, 필수 항목 수, 최근 규정 변경 | `상담 화면으로 이동` |
| 3. 세션 오픈 | 상담 화면으로 이동한다 | 서버 사용 시 `POST /api/sessions` 후 WebSocket 연결. 서버 실패 시 로컬 세션 유지 | 연결 중/연결됨/로컬 폴백, 세션·팩 상태, 대시보드 | LIVE는 녹음 버튼, REPLAY·TRACE는 자동 재생, TEXT는 입력 |
| 4. WebSocket 준비 | 화면에 머문다 | `hello` 또는 `resume`; 서버가 `ready`와 required 항목을 전송 | 선택된 `session_id`, `pack_version`, required 체크리스트, 서버 연결 상태 | 입력을 시작 |
| 5. 녹음 시작 | LIVE에서 `녹음 시작`을 누른다 | 브라우저 `getUserMedia` → PCM 캡처. 프론트는 100ms 바이너리 프레임을 전송 | 녹음 중, 경과 시간, 입력 연결 상태, 녹음→전사→판정→근거 진행 표시 | 상담을 계속하거나 같은 버튼으로 녹음 중지 |
| 6. 음성 전송 | 상담한다 | 프레임은 `4-byte big-endian seq + 16kHz mono PCM16 3,200-byte payload`; 서버 STT가 처리 | 짧은 partial 전사, 최종 전사, 화자(은행원/고객), 시각 | 다음 발화 또는 개입 확인 |
| 7. 전사 확정 | 발화가 끝난다 | `utterance` 이벤트 저장. 서버는 PII 마스킹 후 최종 텍스트를 이벤트에 남김 | 상담 흐름에 누적된 발화, 강조된 문제 문장, 시간 | 판정 결과 대기 |
| 8. 판정 | 서버가 발화를 분석한다 | `Pipeline.submit_utterance`가 `judge → apply → persist → publish`; `verdict`, `alert`, `assist`, `progress` 발생 | 필수 안내 상태 `고지/부분/미고지`, 개입 필요 수, 위반·경보, 남은 항목, 전문용어 밀도, 근거 연결 여부 | 가장 위의 개입 한 건을 확인 |

| 13. 녹음 종료 | LIVE에서 녹음 버튼을 다시 누르거나 상담을 끝낸다 | `MediaStream` 종료; 녹음 자체는 서버 영속 이벤트가 아님 | 녹음 중지 상태, 마지막 전사·판정 상태 | 상담 계속 또는 `상담 종료` |

## 5. 랜딩·브리핑에서 보여 주는 정보

### 5.1 랜딩(L0)

랜딩은 설명용 서비스 페이지다. 실제 상담 입력·판정은 랜딩에서 실행하지 않는다.

- 헤더: 말틈 로고, `말틈이 필요한 이유`, `작동 방식`, `상담 화면`, 세션 이력, 상담 시작 CTA
- 히어로: 서비스 가치 문장과 상담 흐름의 시각적 미리보기
- 설명 섹션: 누락 방지, 문장·숫자 기준 확인, 근거가 남는 상담이라는 세 가지 가치
- 작동 방식: 브리핑 → 상담 화면 → 종료 리포트의 짧은 흐름
- 제품 미리보기: 전사, 현재 개입, 체크리스트, 근거 화면을 축약한 이미지형 카드
- CTA: `상담 시작하기` 또는 `브리핑 확인 후 녹음 시작`
- 랜딩과 브리핑에는 별도의 시연 환경 설정 폼을 표시하지 않는다. 기획서의 `replay`는 지원 모드로 유지하고, 현재 기본 입력은 사용자가 지정한 `LIVE` 녹음 시작 경로를 사용한다.

랜딩에는 튜토리얼 오버레이가 없고 마이크 권한을 요청하지 않는다. 튜토리얼은 대시보드에 진입한 뒤에만 열린다.

### 5.2 상담 전 브리핑

브리핑은 상담원이 화면에 들어가기 전에 읽는 운영 요약이다. 다음 정보를 보여 준다.

1. 기본 시연 시나리오의 상품·실행 모드·팩 버전
2. 필수 안내 항목 수
3. 최근 규정 변경

상품 2종과 `live`·`replay`·`trace`·`text`는 기획서와 서버 계약에 정의된 시나리오·실행 모드다. 그러나 기획서에 사용자가 직접 조정하는 `시연 환경 설정` 패널은 정의되어 있지 않으므로 브리핑에서는 현재 실행 시나리오를 확인하고 상담으로 이동한다.

금지 표현·위험 신호는 브리핑에 미리 나열하지 않고, 상담 중 판정 결과가 발생했을 때 대시보드 개입으로 보여 준다. 필요 서류는 별도 서류 안내 기능에서 표시한다. 브리핑은 필수 항목 수와 최근 변경만 확인하는 단계이며, LLM으로 새 규정을 만들어 내는 단계가 아니다. 현재 백엔드는 `cached=false`를 반환하고 매번 팩에서 접는다.

## 6. 대시보드 한 화면의 정보 구조

데스크톱 대시보드의 원칙은 `녹음 상태 → 현재 개입 → 요약 → 전사·체크리스트 → 근거` 순서다. 바깥 페이지는 100vh에서 잘리고, 화면 안에서 정보 목록만 제한적으로 스크롤한다.

| 영역 | 사용자에게 보이는 정보 | 사용자의 핵심 행동 |
| --- | --- | --- |
| 상단 헤더 | 현재 상담, 상품명, 서버 연결 상태, LIVE/REPLAY/TRACE/TEXT, 경과 시간, 상담 종료, 새 상담 | 종료·새 상담 |
| 녹음·분석 strip | 녹음·전사·판정·근거 단계, 현재 상태, 진행 시간/전체 시간, 진행률 | 단계 확인 |
| 런타임 banner | 연결 상태, partial/STT 상태, 마이크 오류, 재연결, TEXT 폴백, `녹음 시작/중지`, assist 요청 | 녹음 토글, 폴백, 재연결 |
| 현재 개입 | 한 번에 가장 중요한 개입 한 건. 문제 발화, 기준값/기준문장, 심각도, 출처 | 확인 기록, 확인했어요, 근거 보기 |
| 상담 흐름 | 은행원·고객 발화, 시각, 강조 발화, partial 또는 빈 상태 | 맥락 확인 |
| 규정 질의 | 질문 입력, 근거 있는 답변, 원문 연결 또는 근거 없음 안내 | 규정 질의 |
| 진행 상태 | 필수 항목별 고지/부분/미고지/제외, 완료 수/전체 수, 전문용어 밀도 | 항목 선택, 완료 기록, 범위 제외 |
| 선택 항목 근거 | 문서명, 페이지, span, 출처 ref, 원문 전체 보기 | 근거 모달 열기 |
| 하단 상태 | 서버 append-only 이벤트인지 로컬 폴백인지, 팩 버전, 다음 이벤트 또는 완료 | 상태 신뢰도 확인 |

대시보드 튜토리얼은 다음 8개를 순서대로 가리킨다.

1. 상단 전체 상태
2. 녹음·분석 진행 strip

화면 폭 960px 이하에서는 반응형으로 세로 배치되어 페이지 스크롤이 생길 수 있다. 데스크톱에서만 “한 화면·내부 목록 제한 스크롤”이 보장된다. 현재 내부 스크롤 대상은 전사, 체크리스트, 근거, 개입 내용, 질의 답변이다.

## 7. 입력 이벤트와 출력 이벤트의 대응

### 7.1 WebSocket 입력

| 사용자·클라이언트 입력 | 계약 메시지 | 서버 동작 |
| --- | --- | --- |
| 새 연결 | `hello` | 모드·팩·고객 프로필로 준비. `ready` 반환 |
| 끊긴 세션 이어 보기 | `resume` | `session_id`와 마지막 seq 이후 이벤트 재전송 |
| 녹음 오디오 | 바이너리 audio frame | seq·PCM 규격 확인 후 STT 입력 |
| 텍스트 발화 | `text_utterance` | 음성과 같은 `submit_utterance` 판정 경로 |
| 규정 질문 | `ask` | 근거 기반 answer 시도 |
| 도움 요청 | `assist_request` | `rephrase/documents/briefing` 보조 요청 |
| 필수 항목 완료 | `mark_met` | 사람의 verdict 이벤트 기록 |
| 필수 항목 제외 | `mark_waived` | 제외 상태와 사유 기록 |
| 경보 확인 | `acknowledge` | 경보를 supersede하는 확인 기록 |
| 상담 종료 | `end` | `session_ended`, summary, report 생성 |
| 연결 확인 | `pong` | heartbeat 응답 |

### 7.2 서버 출력

| 출력 | 저장 여부 | 프론트 표시 |
| --- | --- | --- |
| `ready` | 세션 시작 전송과 함께 상태에 반영 | 팩 버전·required 체크리스트 |
| `partial` | 저장하지 않음 | 현재 임시 전사 |
| `utterance` | 저장 | 최종 전사·화자·시각 |
| `verdict` | 저장 | 항목 상태·missing elements·근거 ref |
| `alert` | 저장 | 현재 개입 카드·경보 수·위반 수 |
| `assist` | 저장 | 재진술·답변·서류·브리핑 지원 |
| `progress` | 이벤트 원본이 아니라 계산된 상태 | 완료 수·부분 수·남은 항목·용어 밀도 |
| `ended` | `session_ended`로 저장 | 상담 종료·리포트 이동 |
| `error` | 오류 자체는 세션 이벤트가 아님 | STT 장애, 잘못된 메시지, 팩 없음, 세션 만료 등 |
| `ping` | 저장하지 않음 | 클라이언트가 `pong` 응답 |

이벤트 저장의 기준은 `back/contracts/events.schema.json`이다. 원본 이벤트는 append-only이고, 정정은 기존 이벤트를 덮어쓰지 않고 `supersedes`를 가진 새 이벤트로 남긴다. 프론트에서 보이는 현재 상태는 이 이벤트들을 접은 파생 상태다.

## 8. 판정·상태·근거의 의미

### 8.1 세 축

| 축 | 의미 | 사용자에게 보이는 상태 |
| --- | --- | --- |
| omission | 필요한 설명을 했는가 | `met`, `partial`, `unmet`, 사람이 기록한 `waived` |
| commission | 금지 표현·잘못된 숫자를 말했는가 | 위반/경보와 개입 카드 |
| comprehension | 고객이 이해했는지 확인했는가 | 참고 신호. 단독으로 “이해함”의 증거라고 표시하지 않음 |

위험 신호는 고객 발화에서 나온 위험을 별도 경보로 표시한다. 위험 신호 자체를 필수 고지 verdict로 세지 않는다.

개입이 동시에 겹칠 때의 표시 우선순위는 `위험 신호 > 금지 표현 > 숫자 불일치 > 재진술 > 근거 답변 > 누락 넛지 > 전문용어 밀도`다. 대시보드에는 여러 카드를 한꺼번에 펼치지 않고 현재 가장 중요한 한 건을 크게 보여 주어 상담원의 다음 행동을 하나로 좁힌다.

### 8.2 근거 ref

계약의 `evidence_ref`는 일반 문서 ID가 아니라 근거가 붙은 이벤트의 `event_id`다. `GET /api/evidence/{evidence_ref}`가 문서 ID, 페이지, 원문 span, 법적 근거, 페이지 이미지와 bbox를 반환한다. 프론트는 bbox 좌표계의 PDF y축 차이를 보정해 원문 모달에 표시한다.

근거가 없는 답변은 생성하지 않는 것이 원칙이다. 따라서 질의에 맞는 근거가 없으면 답변 대신 확인 필요 메시지를 보여 주고, 근거 없는 문장을 리포트의 증빙으로 만들지 않는다.

## 12. 현재 구현과 목표 사이의 차이

이번 연결 작업으로 핵심 유저플로우의 구현 갭을 다시 닫았다. 남은 항목은 실제 외부 어댑터·운영 인증처럼 프론트 코드만으로 보장할 수 없는 범위다.

| 상태 | 항목 | 현재 동작 |
| --- | --- | --- |
| 해결 | 상품·팩 불일치 | 프론트가 `ICBC-KRW-TD / DEP-2026.08-v6`와 `HNB-HOUSEHOLD-CREDIT / LOAN-2026.08-v7`를 사용하고 서버 preset·briefing과 맞춘다 |
| 해결 | LIVE 시작 행동 | LIVE에서는 브리핑 후 대시보드의 `녹음 시작` 버튼을 눌러야 마이크가 켜지도록 문구·튜토리얼·실행을 일치시켰다 |
| 해결 | 서버 TRACE | 서버 이력의 `TRACE 재생`은 `POST /api/sessions`에 `source_session_id`를 보내고 서버 WS를 연결한다 |
| 해결 | replay preset | preset 목록을 조회하고 `audio_ref`를 세션 생성에 전달한다. 시연 자산 경로도 안전한 기본값으로 보완한다 |
| 해결 | 브라우저 API 연결 | 로컬 `.env.local`의 API base를 same-origin `/api`로 두고 Next rewrite가 `localhost:3000 → 127.0.0.1:8000` REST 요청을 전달한다. WebSocket은 별도 WS URL로 연결한다 |
| 유지 | WebSocket 수동 보완 | `mark_met/mark_waived`는 빠른 상담 화면을 위해 낙관적으로 반영한다. 서버 거절 시 반환 오류를 별도 표시하는 것은 후속 보완이다 |
| 유지 | 리포트 상세 | 요약 카드는 화면 상태를 즉시 보여주며, 서버 report는 수신·PDF·이벤트·근거 연결에 사용한다. 모든 report 섹션의 전용 시각화는 후속 범위다 |
| 유지 | 문서 운영 | 관리자 bearer token이 있어야 업로드·후보 승인·팩 발행이 가능하며, 프론트 API는 설정된 `NEXT_PUBLIC_MALTEUM_ADMIN_TOKEN`을 전송한다. 팩 발행 전용 실행 버튼은 후속 범위다 |
| 유지 | 새로고침 복원 | 서버 세션 자동 resume은 아직 라우팅과 별도로 구현하지 않았고, 종료 이력은 localStorage와 서버 목록을 합쳐 표시한다 |
| 환경 의존 | 실제 음성 판정 | 마이크 권한과 STT key가 준비되면 서버 이벤트로 이어진다. STT가 없으면 녹음 상태는 표시하되 TEXT 폴백을 안내한다 |
| 환경 의존 | LLM·임베딩·소음 | 설정이 없으면 서버의 규칙 fallback이 동작하며, 실제 창구 소음·겹침·숫자 ITN은 외부 어댑터 검증이 필요하다 |

### 12.1 지금 바로 “연결되었다”고 말할 수 있는 범위

- 서버가 정상이고 올바른 pack/session을 선택한 경우: 브리핑 조회, 세션 생성, WebSocket 연결, text/live utterance 입력, 서버 verdict/alert/assist/progress 수신, human mark/ack, evidence 조회, end/report/events 조회가 계약 경로에 있다.
- 실제 마이크 입력: 브라우저 권한과 STT provider가 모두 준비되어야 최종 전사·판정·이벤트 저장까지 이어진다.
- replay: 세션 생성 시 유효한 `audio_ref` 또는 서버가 찾을 수 있는 preset 오디오가 있어야 한다.
- trace: 서버 이력의 `TRACE 재생` 버튼은 source session 기반 `POST /sessions`를 사용한다. 로컬 브라우저 이력은 원본 서버 ID가 없으므로 기존 로컬 trace 폴백으로 재생한다.
- 문서 운영: 읽기·업로드·후보 승인 요청에는 API helper와 bearer header가 연결되어 있다. 실제 성공 여부는 `APP_ADMIN_TOKEN`과 백엔드 추출 산출물에 달려 있으며 팩 발행 실행 UI는 아직 없다.

## 13. 백엔드·계약 기준의 저장 경계

저장되는 것과 저장되지 않는 것을 화면 문구에도 반영해야 한다.

- 저장: `session_started`, 최종 PII 마스킹 utterance, verdict, alert, assist, session_ended, 사람의 완료·제외·경보 확인에 해당하는 이벤트
- 저장하지 않음: raw audio, partial transcript, 마이크 permission 자체, heartbeat
- 파생 상태: 세션 목록·진행 상태·리포트는 append-only 이벤트를 접어 만든 결과
- 팩: 발행된 JSONB 기준은 불변이며, 새 발행은 새 버전
- 후보: 문서에서 파생되며, `span_verified=false` 후보는 승인할 수 없음

따라서 “녹음 중” 표시만으로 녹음 파일이 저장되었다고 안내하면 안 되고, “서버 이벤트·append-only”가 보일 때만 상담 분석 결과가 서버 이벤트로 남았다고 안내해야 한다.

## 15. 구현·검증 시 지켜야 할 순서

새 기능을 넣을 때는 다음 순서를 깨지 않는다.

1. 해당 행동이 어느 사용자 플로우의 어느 단계인지 정한다.
2. `events.schema.json`, `ws_protocol.schema.json`, `api.openapi.yaml`에 입력·출력·저장 여부가 있는지 확인한다.
3. 현재 발행 팩과 시나리오 fixture의 상품명·팩 버전·item code·evidence를 확인한다.
4. 백엔드는 이벤트를 source of truth로 저장하고, 프론트는 서버 progress/state와 폴백 상태를 구분한다.
5. 화면에는 사용자가 다음에 해야 할 행동을 한 가지로 보여 준다.
6. 근거 없는 문장, 미검증 숫자, 원문에 없는 span을 성공 결과처럼 표시하지 않는다.
7. 서버 연결, STT 미설정, 마이크 권한 거부, 재연결, 종료·재생까지 같은 플로우에서 확인한다.

이 순서가 지켜져야 사용자는 “녹음 → 전사 → 판정 → 근거 → 리포트 → 이력 → 새 상담”의 한 줄 흐름을 잃지 않는다.
