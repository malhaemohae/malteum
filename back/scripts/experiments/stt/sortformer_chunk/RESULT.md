# Streaming Sortformer 청크 축소 실험 (CPU, 실제 스트림 재현)

## 재현 명령

```bash
SCRATCH=/tmp/claude-1000/-home-me-projects-malteum/bbf490dd-cf08-4bfa-9747-5dcbfa88b71b/scratchpad/diar

"$SCRATCH/.venv/bin/python" build_result.py   # out_*.json → 아래 표 + table_rows.json
```

가상환경: `$SCRATCH/.venv` (Python 3.11, torch 2.14.0+cpu, nemo_toolkit[asr] 3.0.0, 스레드 4개 고정 `torch.set_num_threads(4)`). GPU 미사용.

## 방법

- 모델: `nvidia/diar_streaming_sortformer_4spk-v2`. 파일 전체를 한 번에 넣는 `model.diarize()` 대신
  `model.forward_streaming_step()` 을 청크마다 직접 호출해 **실제 스트림처럼** 오디오를 시간 순으로 밀어 넣었다
  (참고: `nemo/agents/voice_agent/pipecat/services/nemo/streaming_diar.py` 의 `NeMoStreamingDiarService` 구조를 따르되,
  그 파일이 import 시점에 요구하는 `pipecat-ai` 패키지는 설치하지 않고 필요한 `AudioBufferer`/`CacheFeatureBufferer` 두 클래스만
  `run_chunks.py` 에 그대로 옮겨왔다).
- 청크 길이는 프레임(80ms/프레임) 단위로 반올림했다. 요청 15·5·2·1초는 실제로 각각 188·62·25·12 프레임
  (15.04s·4.96s·2.00s·0.96s)이 됐다 — 모두 모델 제약 없이 정상 동작해 대체값이 필요하지 않았다.
- 오른쪽 문맥 등은 모델 기본값을 그대로 두고 청크 길이만 바꿨다: `chunk_left_context=1`, `chunk_right_context=1`
  (프레임=80ms), `fifo_len=0`, `spkcache_len=188`. `CacheFeatureBufferer` 의 좌우 문맥은 참고 구현 기본값
  `left_offset=right_offset=8`(10ms 프레임)을 그대로 사용했다.
- **청크 처리 시간**: 매 청크에서 `bufferer.update()` + `forward_streaming_step()` 을 감싼 `time.perf_counter()` 구간.
- **라벨 지연**: 청크가 실시간으로 도착한다고 가정(청크 i 의 도착 시각 = `(i+1) × 실제청크초`)하고, 처리가 밀리면
  누적되도록(`finish[i] = max(finish[i-1], 도착[i]) + 처리시간[i]`) 큐를 시뮬레이션했다. 각 정답 줄에 대해, 그 줄 구간과
  겹치는 화자가 누적 출력(스냅샷)에 **처음** 나타난 스냅샷의 `finish` 시각에서 줄이 끝난 시각을 뺀 값이다.
  발화 단위로 평균·최대를 냈다.
- **정확도**: 각 정답 줄 구간과 가장 많이 겹치는 예측 화자를 그 줄의 예측으로 삼고(같은 방식이 `sortformer/evaluate.py`
  에도 쓰였다), 예측 화자 ↔ teller/customer 1:1 매핑을 정확도가 최대가 되도록 고른 뒤 맞은 줄 수를 셌다.
  - **최종 정확도**: 스트림이 끝난 뒤의 누적 출력(=전체 파일을 다 본 뒤의 최종 판단)으로 32줄(파일당 16줄)을 채점.
  - **온라인 정확도**: 그 줄이 끝난 시각을 처음 커버한 스냅샷(=그 줄에 대해 나올 수 있는 가장 이른 출력) 하나만으로
    그 줄을 채점. 나중 청크에서 더 정확해지더라도 반영하지 않는다.
  - **되돌림**: 한 줄에 대해 처음 나타난 이후의 스냅샷들에서 그 줄에 배정된 화자가 이전 스냅샷과 달라지는 횟수를 세어
    청크별로 두 음원 합산.
- 원시 출력은 청크 길이별로 `out_<N>s.json` 에 남겼다(청크별 처리 시간, 누적 예측 텐서에서 뽑은 최종 세그먼트,
  줄별 지연·되돌림·예측). 표는 `build_result.py` 가 `out_*.json` 을 모아 `table_rows.json` 과 함께 만든다.

## 해석

- 청크를 15초에서 1초로 줄여도 두 시연 음원(각 16줄, 합 32줄)에서 최종 정확도와 온라인 정확도 모두 4가지 청크
  길이에서 전부 32/32 를 유지했고, 라벨이 나중 청크에서 바뀌는 되돌림도 0건이었다. 예측 화자 수도 항상 정확히 2명.
  이 음원이 화자 사이 무음이 보장된 TTS 시연 조건이라, 청크를 줄여도 정확도가 떨어지지 않은 것으로 보인다
  (CTX-001 에서도 같은 이유로 오프라인 32/32 였음).
- 청크 처리 시간은 청크가 짧아질수록 절대값은 줄지만(0.24s → 0.11s), 청크 길이 대비 비율(실시간 비율)은
  0.016 → 0.117 로 늘어난다. 1초 청크에서도 실시간의 약 8.5배 속도라 CPU 4스레드로 충분히 여유 있다.
- **라벨 지연**은 청크 길이에 거의 비례해서 줄어든다(평균 8.16s → 0.58s). 지연의 대부분은 "다음 청크 경계까지
  기다리는 시간"이고, 청크 처리 시간과 문맥은 상대적으로 작은 비중이다. 실시간 서버에서 지연을 줄이려면
  청크를 줄이는 쪽이 처리 시간을 줄이는 쪽보다 훨씬 효과적이다.
- 피크 메모리는 스윕 전체(모델 1개를 재사용해 청크 길이 4가지 × 음원 2개를 순차 실행)에서 1758 MB로, 청크
  길이와 무관하게 거의 일정했다(모델 자체 크기가 지배적).
- **주의**: 이 결과는 겹침 발화 없는 TTS 시연 음원 기준이다. 실제 창구 녹음(겹침 발화·잡음)에서는 청크를
  줄였을 때 정확도가 여기서보다 더 떨어질 가능성이 높다 — 이 실험만으로 실전 청크 크기를 확정할 수는 없다.
