# Qwen3-ASR-0.6B / 1.7B 한국어 은행 상담 음원 시험 — 2026-09-04

Nemotron 3.5 ASR 실험(`../nv_asr/RESULT.md`)과 같은 음원(`preset-dep-a` 147 s, `preset-loan-b` 128 s), 같은 평가 스크립트(`../nv_asr/merge_eval.py` 를 수정 없이 호출), 같은 Sortformer 화자 결과(`../diar/streaming_out.json`), 같은 핵심 용어 15 개·표기 변형 목록으로 시험했다.

## 1. 모델·도구 조사 (모델 카드 · GitHub QwenLM/Qwen3-ASR · PyPI qwen-asr 0.0.6)

- **구조**: 오디오 인코더 + Qwen3 LLM 디코더(AED 계열). 0.6B 는 실제 0.9B 파라미터(safetensors 1.88 GB), 1.7B 는 약 2B(4.7 GB). Apache-2.0. 30 언어 + 중국어 방언 22, **한국어 포함**.
- **실행 경로**: `pip install qwen-asr` 로 transformers 백엔드(`Qwen3ASRModel.from_pretrained(..., device_map="cpu"|"cuda:0")`) — CPU 에서 그대로 돈다(fp32). vLLM 백엔드(`Qwen3ASRModel.LLM`, `qwen-asr[vllm]`)는 선택이지만 **스트리밍 API 는 vLLM 백엔드 전용**(`init_streaming_state / streaming_transcribe / finish_streaming_transcribe`, transformers 백엔드에서는 `ValueError`). 2026-06 부터 transformers 네이티브 지원도 있음.
- **스트리밍 방식**: 진짜 인과(causal) 인코더 스트리밍이 아니라 **"청크마다 발화 시작부터의 누적 오디오를 다시 넣고, 직전 결과의 마지막 K 토큰을 잘라낸 텍스트를 프리픽스로 주어 이어 쓰게 하는" 재디코딩 방식**이다. 기본값 `chunk_size_sec=2.0`, `unfixed_chunk_num=2`, `unfixed_token_num=5`, 예제는 500 ms~4 s 단위 push. vLLM 의 prefix cache 가 있어야 비용이 감당되므로 vLLM 전용으로 묶어 둔 것. 상태는 "single utterance" 단위라 VAD/화자 분리로 발화를 끊어 주는 구조를 전제한다. 스트리밍에서는 타임스탬프·배치 불가.
- **타임스탬프**: ASR 모델 자체는 단어/문장 시각을 내지 않는다. 별도 모델 `Qwen/Qwen3-ForcedAligner-0.6B`(1.84 GB, 한국어 지원, 최대 5 분)를 `return_time_stamps=True` 로 붙여야 하며 오프라인 전용. 이번 실험에서는 다운로드 상한(6 GB) 때문에 정렬기는 받지 않았고, 대신 Sortformer 세그먼트 단위로 전사해 세그먼트 안에서 단어를 균등 배치했다(아래 "seg" 모드).
- **언어 지정**: `language="Korean"`(None 이면 자동 감지, 출력 `.language` 필드에 감지 언어). 긴 파일은 패키지가 내부에서 최대 1200 s 청크로 자른다.
- **숫자 표기**: 문서에 ITN 언급은 없다. 실측(아래 §4)에서는 **아라비아 숫자를 내기는 하지만 일관되지 않는다** — 긴 문맥에서는 `14%`, `15.4%`, `5%`, `DSR` 을 내고, 2~5 초 짜리 짧은 세그먼트에서는 `십사 퍼센트`, `십오 점 사 퍼센트`, `연 삼 퍼센트` 로 낸다. 0.6B 는 `14퍼센트`, `15점 4퍼센트`, `연3퍼센트` 같은 혼합형도 낸다.

## 2. 환경

- RTX 4070 12 GB(주 수치) + CPU 24 코어/30 GB(참고). 프로젝트 코드는 건드리지 않음.
- `qwen_asr/.venv`(CPU torch 2.14.0+cpu, transformers 4.57.6, qwen-asr 0.0.6), `qwen_asr/.venv_gpu`(CUDA torch, 같은 패키지). `../diar/.venv` 는 transformers 5.16 이라 qwen-asr(4.57 요구)와 충돌해 새로 만들었다.
- **vLLM 설치 실패**: `qwen-asr[vllm]`(Python 3.12) 설치가 CUDA 휠(cupy, cudnn, triton …)을 받다가 `/tmp`(tmpfs) 로의 파일 복사 오류로 중단(`install_vllm.log`). 시간 상한 안에 재시도하지 않았다. 따라서 **공식 스트리밍 API 는 직접 못 돌렸고, 그 알고리즘을 transformers 백엔드 위에 그대로 재현한 시뮬레이션**(`run_stream.py`: 2 s 청크, 누적 오디오 재투입, 마지막 5 토큰 롤백, Sortformer 세그먼트를 발화 단위로 상태 초기화)으로 지연·정확도를 쟀다. vLLM 을 쓰면 prefix cache 로 스텝당 계산이 더 줄어들 뿐 출력은 같은 프롬프트라 크게 다르지 않을 것으로 본다.
- 다운로드: 0.6B 1.88 GB + 1.7B 4.7 GB = 6.6 GB(정렬기는 제외해 상한 근처에서 멈춤). 설치·실행 시간은 모델당 25 분 미만.

## 3. 방법 (세 가지 입력 방식 × 두 모델)

| 모드 | 입력 | 시각 정보 | 용도 |
|---|---|---|---|
| full | 파일 전체 한 번에 | 없음 → 줄별 CER·화자 산출 불가, 전체 CER·용어만 | 모델의 "최선" 정확도 |
| seg | Sortformer 세그먼트(35/27 개)를 잘라 배치 전사, 세그먼트 안 균등 배치 | 세그먼트 경계 | **현실 파이프라인**(화자 분리 → 발화별 전사)과 같음 |
| clips | 정답 줄 경계 클립 16 개 | 줄 경계(오라클) | 분할 오류 없는 상한 |
| stream | seg 와 같은 발화 단위 + 2 s 청크 스트리밍 시뮬레이션 | 세그먼트 경계 | 지연·정확도 |

CER 은 공백·문장부호 제거 후 글자 Levenshtein / 정답 글자 수. "화면 표기"는 `text`, "발음 표기"는 `tts_text`(있는 줄만) 기준.

- 스트리밍 알고리즘 지연 = 청크 2 s + 스텝 계산(GPU 0.14~0.16 s, CPU 0.6 s 평균·1.2 s 최대; 누적 오디오가 길수록 커진다). 첫 글자가 나오기까지 최소 2 s 라 Nemotron 의 0.32 s 청크(0.4 s 지연)보다 체감 지연이 크다. 청크를 0.5 s 로 줄이면 스텝 수가 4 배가 되고 매 스텝 누적 오디오를 재인코딩하므로 CPU 에서는 실시간을 넘길 가능성이 크다(vLLM prefix cache 없이는 특히).
- CPU 에서 Qwen 0.6B 는 Nemotron 보다 오프라인 4~5 배 느리다(LLM 디코더 자기회귀). GPU 가 있으면 문제가 안 된다.

## 6. 판단 — 무엇을 Deepgram 대체 후보로 삼을지

GPU(RTX 4070 급)가 있는 서버라면 **Qwen3-ASR-1.7B + Streaming Sortformer(발화 분할) 조합**이 첫 후보다. 이 음원에서 핵심 용어 15 개를 모두 잡았고(Nemotron 12, 0.6B 13), 화면 표기 기준 CER 이 가장 낮으며, `14%`·`15.4%`·`DSR` 처럼 판정에 쓰는 수치·약어를 아라비아 숫자/영문으로 내는 유일한 모델이라 ITN 후처리 부담이 가장 작다. 다만 세 가지 단서가 붙는다. (1) 스트리밍이 vLLM 전용의 "2 s 청크 재디코딩" 방식이라 첫 응답 지연이 2 s 이상이고 vLLM 설치·GPU 상주(약 5 GB)가 필요하다 — 이번에 vLLM 설치가 실패해 시뮬레이션으로만 확인했다. (2) 시각 정보가 없어 화자 결합은 Sortformer 세그먼트로 오디오를 잘라 넣는 구조로만 가능하고, 오프라인 후처리에는 ForcedAligner(1.8 GB)를 하나 더 얹어야 한다. (3) 숫자 표기가 문맥 길이에 따라 흔들리고(`15.4%` vs `십오 점 사 퍼센트`), full 모드에서 `1억`→`2억`, `3%`→`연산 %` 같은 금액·비율 오류가 한 번씩 나왔으므로 숫자는 어느 모델이든 별도 검증 규칙이 필요하다. CPU 만 있는 서버라면 순서가 바뀐다: Qwen 0.6B 조차 CPU 에서 Nemotron 보다 4~5 배 느리고 2 s 청크 스트리밍은 CPU 실시간을 장담 못 하므로, **Nemotron 3.5 ASR(0.32 s 청크, CPU 실시간 여유) + Sortformer + 한국어 ITN** 이 현실적인 선택이다. Qwen3-ASR-0.6B 는 정확도가 1.7B 와 Nemotron 사이(용어 13/15, `DSR`→`DSL`)이고 GPU 메모리를 2.6 GB 만 쓰므로, GPU 가 작거나 여러 스트림을 동시에 받아야 할 때의 절충안이다.

## 7. 파일

- `run_offline.py <model> <tag>`(env `DEV=cpu|cuda:0`) → `offline_{06b,06b_gpu,17b_gpu}.json`(full/seg/clips 세 모드), 로그 `offline_*.log`
- `run_stream.py <model> <tag> [chunk_s]` → `stream_{06b_gpu,17b_gpu,06b_cpu}.json`(CPU fp32 스트리밍 정확도는 GPU bf16 과 거의 같음: dep-a 6.6 %, loan-b 4.4 %)(스텝별 지연·부분 텍스트), 로그 `stream_*.log`
- `eval_qwen.py <json>` → `../nv_asr/merge_eval.py` 를 그대로 호출해 `eval_<tag>_<mode>.txt`(줄별 GT/HYP 대조) · `.json`
- 모델 카드/README 사본 `qwen3asr_README.md`, 공식 스트리밍 예제 `example_vllm_streaming.py`, 설치 로그 `install*.log`
- 가상환경 `.venv`(CPU), `.venv_gpu`(CUDA), `.venv_vllm`(설치 실패, 미완성)
