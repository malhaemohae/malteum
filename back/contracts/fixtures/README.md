# fixtures · 계약 테스트

스키마는 "필드가 있다" 까지만 보장한다. **이 폴더가 "값이 맞다" 를 보장한다.**

| 파일 | 무엇 | 누가 쓰나 |
| --- | --- | --- |
| `rulepack_DEP-2026.08-v3.json` | 규정 팩 실물 1건. 항목 9개 | M3 발행 결과의 정답 · M2 로드 테스트 입력 |
| `events_scenario_a.json` | 시연 시나리오 A 의 이벤트 열 27건 | trace 재생 · 리포트 생성 · 접기 함수 테스트 |
| `ws_messages.json` | c2s·s2c 메시지 25건 | M4 프런트 개발 시 서버 없이 화면 그리기 |
| `judge_cases.json` | 판정 입출력 쌍 13건 | M2 엔진의 통과 기준 |

## 값이 실물이다

`rulepack` 과 `events` 의 인용 문자열·페이지·bbox 는 `03_규정문서/` 의 실제 PDF 에서 뽑았다.
`validate.py` 3층이 매번 원문과 대조하므로 **꾸며낸 인용은 커밋을 통과하지 못한다.**

```bash
python contracts/validate.py
```

숫자도 실물이다. 중도해지 이자율 1개월 미만 연 0.10%, 예금자보호 5천만원, 일부해지 2회.

## 시나리오 A 가 담고 있는 것

시연에서 보여줄 네 장면이 모두 이벤트로 들어 있다.

| 시점 | 무엇 | 이벤트 |
| --- | --- | --- |
| 0:35 | 숫자 오류 | `EV-0005` alert `number_mismatch` (0.5% vs 연 0.10%) |
| 1:10 | 되물음 → 재진술 | `EV-0009` assist → `EV-0011` 이 `outcome=adopted` 로 대체 |
| 1:50 | 금지 발언 | `EV-0015` suspected(L1) → `EV-0017` violated(L3) |
| 2:15 | 정정 | `EV-0006` partial → `EV-0019` met(L3) |
| 종료 | 누락 2건 | 예금자보호 한도 · 만기 후 이자율 |

`supersedes` 체인이 세 군데 있다. 화면과 리포트는 **대체되지 않은 마지막 이벤트만** 읽는다.
`validate.py` 가 종료 요약을 이벤트에서 다시 접어 대조하므로, 접기 규칙을 잘못 구현하면 즉시 드러난다.

## id 규칙

fixture 의 id 는 `FIXT-` 로 시작한다. 실제 운영은 ULID 를 쓴다.
접두어를 다르게 둔 이유는 fixture 데이터가 운영 DB 에 섞였을 때 눈으로 바로 구분되게 하려는 것이다.

## 판정 케이스가 고정하는 것

`judge_cases.json` 은 통과·실패만 보는 표가 아니다. 각 케이스의 `why` 가 **왜 이 동작이어야 하는지**를 적어 둔 것이고,
그것이 나중에 "이건 왜 이렇게 돼 있지" 를 막는다. 특히 다음 네 개는 하나라도 깨지면 제품이 못 쓰게 된다.

- 인용된 금지 표현은 위반이 아니다 (화자를 보지 않으면 즉시 오탐)
- 숫자가 맞으면 경보가 없다 (오탐이 쌓이면 은행원이 경보를 무시한다)
- 화자 신뢰도가 낮으면 met 로 올리지 않는다 (잘못된 met 가 잘못된 unmet 보다 위험)
- 근거를 못 찾으면 답하지 않는다 (없는 근거를 만들면 그게 제일 나쁜 실패)

`tier` 와 `max_ms` 는 성능 계약이다. L1 5ms, L1+L2 20ms, L3 1500ms.
