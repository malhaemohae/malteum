# contracts · 모듈 간 계약

**상태: 초안 전체 작성 완료 (2026-08-24) · 동결 목표 2026-08-28**

이 폴더가 네 모듈의 유일한 접점이다. 여기 있는 파일만 지키면 서로의 코드를 볼 일이 없다.

## 파일

| 파일 | 경계 | 무엇 |
| --- | --- | --- |
| `events.schema.json` | M1·M2 → DB | **세션 이벤트.** 영구 저장물. append-only. 증빙·재생·복구·감사의 원본 |
| `ws_protocol.schema.json` | M1 ↔ M4 | **WebSocket 메시지.** 휘발성 전송물. 화면을 그리기 위한 형태 |
| `rulepack.schema.json` | M3 → M2 | **규정 팩.** M3 가 만들고 M2 가 읽는다. 불변 발행물 |
| `api.openapi.yaml` | M1 ↔ M4 | REST. 실시간이 아닌 조회·업로드·승인·산출물 |
| `engine_contract.py` | M1 ↔ M2 | 타입과 시그니처. 같은 프로세스 안의 유일한 접점 |
| `fixtures/` | 전원 | 실물 값이 든 예시. **이것이 계약 테스트다** |
| `validate.py` | 전원 | 3층 검증. 커밋 전에 돌린다 |
| `find_span.py` | M3 · 검증 | 인용 문자열 → 페이지·문자 좌표. **P4 의 기계적 관문** |

호출 방향을 한 줄로:

```
M3 ──rulepack──▶ M2 ◀──engine_contract── M1 ──ws_protocol──▶ M4
                  │                       │                    │
                  └────────events─────────┴──api.openapi───────┘
                                 ▼
                                 DB
```

## 동결 규칙

- **8/28 이후 변경은 전원 합의.** 한 사람이 고치면 네 모듈이 동시에 흔들린다
- 변경 시 `fixtures/` 를 함께 갱신하고 `validate.py` 를 통과시킨다
- `events.schema.json` 은 특히 신중히. 이미 쌓인 이벤트를 읽지 못하게 되면 재생·감사가 죽는다. 그래서 모든 이벤트에 `schema_version` 이 있다
- 필드 **추가는 안전**(옵셔널로), **삭제·의미 변경은 위험**

## 전송과 저장을 왜 나누나

같은 판정을 담지만 목적이 달라 형태가 다르다.

| | ws_protocol | events |
| --- | --- | --- |
| 수명 | 연결이 끊기면 사라짐 | 불변 · 영구 |
| 방향 | 있음 (`c2s`/`s2c`) | 없음. 일어난 사실 |
| 목적 | 화면 그리기 | 증빙 · 재생 · 복구 · 감사 |
| `seq` | 연결 단위 순번 (재접속에 필요) | 없음 (`seq_in_session` 이 대신) |
| `pack_version` | 세션 시작 시 1회 | **모든 이벤트에** (낱개로 해석돼야 함) |
| partial 전사 | 보냄 | **저장 안 함** |
| 오디오 프레임 | 보냄 (바이너리) | 저장 안 함 |
| 하트비트 | 보냄 | 저장 안 함 |

**ws 메시지를 그대로 저장하지 않는다.** 프로토콜 관심사가 저장물에 섞이면 프로토콜을 바꿀 때 과거 데이터를 못 읽는다.
**이벤트를 그대로 전송하지 않는다.** 프런트가 필요한 형태와 감사가 필요한 형태가 다르다.

변환은 **M1 이 한다.** M2 는 이벤트를 만들고 WebSocket 을 모른다. 그래야 판정 엔진을 네트워크 없이 테스트할 수 있다.

## 이벤트를 상태 대신 저장하는 이유

상태(체크리스트 현재 모습)만 저장하면 간단하지만 잃는 것이 크다.

| | 상태 저장 | 이벤트 저장 |
| --- | --- | --- |
| 리포트 | 최종 상태만 | 언제 무엇이 어떻게 바뀌었는지 |
| trace 재생 | 불가 | 가능 |
| 잘못된 판정 | 덮어써서 흔적 없음 | 기록에 남고 정정 이벤트가 추가됨 |

**상태는 이벤트를 접어서 다시 계산할 수 있지만, 이벤트는 상태에서 복원할 수 없다.** 이벤트가 원본이고 상태는 파생물이다. 회계 장부가 잔액을 고치지 않고 거래를 추가하는 것과 같은 구조이며, 업계에서는 event sourcing 이라고 부른다.

성능 우려는 없다. 실시간 화면은 메모리에 상태를 들고 있고, 이벤트는 그와 별도로 쌓는다. 리포트는 세션 종료 후 한 번만 접는다.

## 갱신 이력을 표현하는 방법

append-only 라서 고칠 수 없다. 나중에 밝혀진 사실은 **새 이벤트로 기록하고 `supersedes` 로 앞선 것을 지목**한다.

```
verdict  L2 판정: partial            event_id=A, supersedes=null
verdict  L3 보정: met                event_id=B, supersedes=A
```

화면과 리포트는 **supersede 되지 않은 마지막 이벤트만** 읽는다. 같은 패턴을 `assist` 에도 쓴다. 제시할 때 `outcome=null` 로 발행하고, 은행원이 그 표현을 실제로 썼는지 확인되면 `outcome` 을 채워 다시 발행한다.

## 검증

```bash
python contracts/validate.py
```

세 층으로 본다. 뒤로 갈수록 스키마가 못 잡는 것을 잡는다.

| 층 | 무엇을 보는가 | 없으면 |
| --- | --- | --- |
| 1 스키마 | fixtures 가 JSON Schema 를 만족하는가 | `pip install jsonschema` 없으면 건너뜀 |
| 2 교차 | 팩에 없는 항목 코드, 요약과 실제 판정의 불일치, `supersedes` 끊김, ready 항목 집합 | 항상 수행 |
| 3 근거 실재 | `evidence.span` 이 실제 PDF 그 페이지에 있는가, bbox 가 맞는가 | `pip install pypdfium2` 없으면 건너뜀 |

**3층이 가장 중요하다.** 스키마는 문자열이 있다는 것까지만 보장하고 그 문자열이 원문에 실재한다는 것은
보장하지 못한다. 근거 없는 항목이 팩에 들어가면 화면에는 그럴듯한 인용이 뜨지만 원문에는 없다.
이 제품에서 가장 나쁜 실패이므로 기계가 막는다 (P4).

좌표를 뜨는 함수는 `find_span.py` 하나다. **M3 의 팩 발행 파이프라인도 이 함수를 써야 한다.**
다른 구현을 쓰면 그쪽에서는 통과하고 여기서는 실패하는 팩이 나온다. 그래서 이 파일은 도구가 아니라 계약이다.
